# Bead bf-4ijd: Test Overlay Rendering with Real OG Images

## Goal
Verify the semi-transparent cropper overlay renders correctly against real OG
image files — position matches the safe zone, dimensions match `calculateSafeZone()`,
and the transparency actually renders (both the on-screen SVG path and the
canvas-export PNG path).

## What was done
Added `test/e2e/overlay-rendering.e2e.js` — a Playwright e2e that drives the
REAL `updateCropperOverlay()` / `exportCropperOverlay()` in `app.js` (served
same-origin from `src/public`) against rasterized OG fixtures generated by sharp.

Two rendering paths covered (the unit tests in `test/unit/safe-zone.test.js`,
bf-3n2m, only cover the pure geometry helpers — no DOM, no canvas, no pixels):

1. **On-screen SVG** — `updateCropperOverlay()`. For each scenario: load a real
   fixture, populate `cropperState`, call the real overlay fn, then read back the
   `<rect>` attributes and compare against an independent Node-side
   `calculateSafeZone()` (a separate module instance fed the real `PLATFORM_CROPS`
   specs read out of the page — a real cross-check, not the browser vs itself).
2. **Canvas export** — `exportCropperOverlay()`. Trigger the real export, capture
   the download, and measure rendered alpha against the base fixture
   (source-over inversion: `a = (out-base)/(overlay-base)`).

## Scenarios (7 SVG + 1 export)
1200×630 fb+pinterest, 1200×630 fb-only, 1200×1200 square cross, 2000×600 sides-cropped,
1000×1500 portrait, 2400×1260 retina 2×, 1200×630 ALL-31-platforms; plus a
2000×600 canvas export with measured alpha.

## Result — all 65 checks pass
- SVG `<rect>` safe-zone **position** matches `calculateSafeZone()` to 1e-3
  across every scenario (e.g. 1200×630 fb+pn → `(388.9, 0.9)` `422.1×628.3`).
- SVG `<rect>` **dimensions** match exactly.
- Platform crop rects render semi-transparent (`fill-opacity="0.15"`); safe zone
  is a white dashed stroke (`fill="none" stroke="#ffffff" dash=12,6`).
- Canvas export is at natural image resolution (2000×600, no scaling), with the
  facebook fill at α≈0.257 inside the crop rect and α=0.000 outside it.
- Retina 2× safe-zone fractions are exactly 2× the 1× fractions (linear scaling).

### Pixel-level confirmation of the 2000×600 export (the acceptance criteria)
A horizontal scanline at y=300 across the exported PNG:
```
x=   0  OUT  α=0.000   ← left strip: no overlay
x= 430  IN   α=0.257   ← overlay starts (expected x=427)
x=1570  OUT  α=(edge)  ← overlay ends (expected x=1573)
```
Overlay covers exactly the centered 1146 px facebook crop, leaving the left/right
~427 px strips clear, at α≈0.25 (=`color+'40'`=0x40/0xff). ✓

Artifacts written to `test-results/overlay-rendering/` (fixtures/, screenshots/,
exports/) for manual review.

## Bug found and fixed in the test itself
The canvas-export block had a short-circuit
`if (img.complete && img.naturalWidth) return resolve();` that returned
**before assigning the new `src`**. After the 7 SVG scenarios the `<img>` still
held the last scenario's image (1200×630 ALL), so:
- the exported PNG was 1200×630 (not the intended 2000×600),
- the alpha check misaligned a 2000-wide base fixture against a 1200-wide export
  → garbage α (1.962 inside, 0.806 outside), masking whether export actually works.

This is the identical bug the SVG-scenario block already documents and fixes
("A previous `if (img.complete && ...)` short-circuit returned WITHOUT assigning
src…"). The export block was simply missed. Fixed by applying the same
always-assign-src pattern. After the fix: 2000×600 export, α=0.240 inside, 0 outside.

## Observation (not a failure) — opacity mismatch between the two views
The on-screen SVG renders crop fills at `fill-opacity="0.15"` while the canvas
export uses `color+'40'` (≈0.25). Both render *correctly*, but the two views of
the same data render at different opacities. Likely intentional (on-screen overlay
is subtle so the image shows through; exported overlay is more visible), but
recorded here in case a follow-up wants them consistent.
